# 数据编写、重载与迁移

## 查清定义和派生内容各自的覆盖规则

- **适用条件** 当你用数据包、Java 注册或脚本扩展同一类内容时。
- **观察到的现象** 你可能看到条目成功读入，玩家最终拿到的产物却来自另一来源，或删除定义后派生配方仍然存在。
- **判断依据** 你需要分别找到定义表和配方管理器的实际装填阶段、覆盖条件与冲突处理。脚本引擎能启动时，才有条件观察其实际提交结果。
- **做法** 你可以给同一 ID 准备可区分的有效输入，分别在启动和 `/reload` 完成后回读，并从实际消费者走一遍查询、解锁或产出。指南按当前分支维护字段、校验和重载限制。
- **反例/坑** 你若把一种定义的优先级当成所有配方的顺序，可能错判冲突。脚本依赖启动失败时，数据包通过也不能证明脚本可用。

## 草稿和有效发布分别保存

- **适用条件** 当你实现可保存、撤回、检查和发布的内容编辑器时。
- **观察到的现象** 你可能看到检查完旧修订后仍可发布已修改的草稿，或撤回界面后运行的资源仍然指向新内容。
- **判断依据** 你要确认修订身份是否覆盖文档、布局与结构的同一次改动，检查结果是否绑定该修订，发布数据是否需要脱离源存档的业务身份。
- **做法** 你可以将保存草稿、检查和发布做成三个显式动作。撤回同步相关资源，检查缺失字段时保留精确原因。先构造完整发布内容，再切换有效结果。
- **反例/坑** 你若用默认坐标吞掉缺失字段，可能成功发布到错误位置。把保存和发布绑在一起，也会让普通保存改写生效内容。

## 在写盘前处理不兼容的语义

- **适用条件** 当你改变字段含义、数据版本或两端消息契约时。
- **观察到的现象** 你可能看到字段类型和长度完全相同，旧端却把同一数值解释成不同动作或位置。拒绝加载过晚时，存档备份可能已经被新端写过。
- **判断依据** 你要查实旧读者对数值的解释、编解码顺序、双方能力识别，以及加载流程中首次可能写盘的位置。
- **做法** 你可以用真实旧样本测试迁移与拒绝，核对无关字段和备份。需要混版时分别运行两个连接方向，确认有能力的端点才读写新语义。
- **反例/坑** 你若只比较 Java 类型或用新编码器配新解码器，可能漏掉旧端误解。写盘后才拒绝也无法保全原有备份。
