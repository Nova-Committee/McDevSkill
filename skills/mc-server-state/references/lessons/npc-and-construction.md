# NPC 会话、交易与施工

## 先核对身份和加载时序

- **适用条件** 当你维护同名 NPC、多人访问、实体恢复或会话续时逻辑时。
- **观察到的现象** 你可能遇到区块已读入而实体查询短暂为空，或界面有点击效果而服务端访问计时未续期。
- **判断依据** 你要区分逻辑 ID、实例 UUID、所属空间与访客身份，确认实体何时注册、动作到达哪一层、哪些动作符合续时条件。
- **做法** 你可以等实体生命周期就绪再判断需要恢复的对象，按玩家核验距离、维度和会话。对照两名访客的记录、界面事件与服务端受理结果，释放自己接管的寻路或朝向。
- **反例/坑** 你若从一次空查询重建实体，可能复制本来会加载的对象。拉长计时也无法补回被界面吞掉的动作。

## 给交易写请求绑定具体物品和回执

- **适用条件** 当你同步多个容器槽、物品带大组件，或确认交易要等待服务端时。
- **观察到的现象** 你可能看到全量堆叠消息超出限制，重试时误绑了新背包，或旧回执清除了当前编辑内容。
- **判断依据** 你需要核对实际包大小与槽同步入口，并区分请求身份、冻结的物品来源和当前界面上下文。
- **做法** 你可以优先复用真实菜单的槽位同步，用轻量请求标识绑定当时上下文。结算前从权威槽位核验物品与精确组件，丢弃过期回执，按实际提交结果扣物和修改库存。
- **反例/坑** 你若让每次开窗或刷新结算，可能重复扣物、重置有限库存。只按显示名或物品 ID 还会丢失组件差异。

## 把选址预览、开工和续建分开

- **适用条件** 当你实现世界选址、收费开工和可冷启恢复的施工时。
- **观察到的现象** 你可能看到悬停预览被误当成已确认地点，被拒后无法重试，或重启后重复收费。
- **判断依据** 你要区分悬停候选、已确认位置、权威模板和已提交的工程。检查申报资源、容量与锚点的验证顺序，以及扣费后的持久记录。
- **做法** 你可以只从已确认候选提交开工请求，并在匹配的拒绝回执后保留候选和原因。服务端先校验、冻结计划，再把提交记录和收费纳入同一可恢复流程。冷启后依记录续建，用隔离世界验证重复请求和加载。
- **反例/坑** 你若把预览状态当作提交凭证，视角一动就可能改了目标。恢复时重新走收费入口也会破坏资源守恒。
