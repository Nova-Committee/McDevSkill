# 全服重生与个人维度落点

## 追到出生点 API 的最终所有者

- **适用条件** 当你为临时或个人维度设置入口，并考虑使用世界对象上的重生点 setter 时。
- **观察到的现象** 你可能看到 A 建界后的入口正常，B 无个人重生点死亡时却出现在 A 的维度。
- **判断依据** 你需要沿目标版本的 `ServerLevel.setRespawnData` 追到写入字段、持久化和通知。若它委托 `MinecraftServer` 并写入全服 world data，改变的是全服重生状态。
- **做法** 你可以把传送落点写入本功能拥有的数据。用 A 建维度并回读全局字段，用 B 分别验证无床与已有床的原版重生，另测 A 与访客的进出。
- **反例/坑** 你若凭方法所在的类推断作用域，容易把全局 setter 当成维度 setter。只测 A 的传送也看不到对 B 的副作用。

## 登记前组装完整落点与回程记录

- **适用条件** 当你支持保存自选落点和朝向、访客访问或安全回退时。
- **观察到的现象** 你可能看到首次使用正常，冷启动后自选点丢失，或访客误用自己的落点、失败传送覆盖了回程点。
- **判断依据** 你要核对登记及标脏时的序列化快照，区分所有者的默认锚点与自选点、每位访客的回程、当前位置与安全判定。
- **做法** 你可以先完整计算并赋值，再登记和标脏。保存时从服务端读实际站位。进入时按约定的顺序核验自选点与默认点，成功前保留回程。用两位玩家重复重入并冷启动同一份隔离存档。
- **反例/坑** 你若先登记再补字段，可能让自动保存拿到半成品。两处都不安全时先写回程记录，也会让一次未完成的传送留下状态变更。

## 处理已经被旧逻辑覆盖的全服状态

- **适用条件** 当你修好了全服写入路径，并需要支持已经受影响的世界时。
- **观察到的现象** 你可能看到升级后新的个人维度不再改写全局字段，旧存档却继续在错误维度重生。
- **判断依据** 你需要确认存档是否留有原维度、坐标和可核验的历史记录。修复写入路径与恢复旧值是两个独立动作。
- **做法** 你可以先在副本验证管理员提供的目标维度和坐标，再按确认的恢复流程执行，并让第二身份复验重生和冷启。
- **反例/坑** 你若根据当前玩家位置猜原坐标，可能把用户已有的自定义重生点再覆盖一次。
